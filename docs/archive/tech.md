# Tech

## Стек
- **Фронтенд**: Phaser 4 + Vite + TypeScript, скаффолд `phaserjs/template-vite-ts`. Деплой — статика на GitHub Pages через `npm run deploy` (пакет `gh-pages`, публикует `dist/` в ветку `gh-pages`), см. `docs/MAP.md`. Vite `base: './'` даёт относительные пути в собранном HTML, под-путь Pages (`/sales-vs-dragon/`) не требует настройки.
- **Бэкенд**: Google Apps Script Web App, привязанный к приватной Google-таблице. Бесплатно, без отдельного хостинга/сервисного ключа. Поля `totalMeters`/`metersRemaining` в его ответе остались с прежней концепции — фронтенд их игнорирует (в `StatusResponse` они опциональные).
- **Рендер**: `pixelArt: true, roundPixels: true` (`src/game/main.ts`), логический размер **1280×720** (`Scale.FIT`, 16:9 — на офисном мониторе без чёрных полос; расширен с 1024×576, чтобы развести персонажей и дракона). Буфер холста в `GAME.RENDER_SCALE` = 2 раза больше — **2560×1440** — см. «Чёткость текста» ниже.
- **Без эффектов свечения и теней у персонажей** — пользователь убрал их как визуально неприятные; заново вводить только по явной просьбе.

## Пайплайн ассетов (character-refs → игра)

Пользователь генерирует персонажей в Fooocus (см. раздел ниже), дорабатывает в Photoshop (вырезание фона, прозрачный PNG) и раскладывает по папкам `game/assets-source/character-refs/` (`СР1 - Лев`, …, `Дракон`, `Круэлла …`). Игра эти файлы напрямую **не грузит** — их обрабатывает `game/tools/build-sprites.py` (Python + Pillow, запуск из `game/`: `python tools/build-sprites.py`) и пишет результат в `public/assets/sprites/`. Что делает скрипт и почему:

- **Обрезка по bbox альфы**, без удаления фона (источники уже с настоящей прозрачностью).
- **Единый пиксельный масштаб внутри героя.** Позы удара (`Анимация 1..3`) нарисованы в другом масштабе, чем «стоячая» поза (у Незнайки ≈ в 2 раза мельче, у Гринча ≈ в 2.3). Коэффициенты (`HEROES` в скрипте) подобраны на глаз по контактному листу голов; после перегенерации персонажа их, возможно, придётся подстроить.
- **Даунскейл LANCZOS до 2× экранного размера** (`TEX = 2`), в игре `scale 0.5` (`HERO.TEXTURE_SCALE`, `Dragon`). Причина: `pixelArt: true` включает NEAREST, а сжимать 1000-пиксельный арт в 6 раз NEAREST-ом даёт шум.
- **Совмещение состояний дракона.** Шесть состояний (5→0 голов) нарисованы отдельно, на холстах разного размера и с разным сдвигом/масштабом (состояние «целый» на ~6% крупнее). Скрипт нормализует холсты по ширине, потом подбирает сдвиг (и при необходимости масштаб) по совпадению маски **правой части тела** (хвост/крыло/задние лапы) с эталоном «без одной головы» — головы не участвуют, они и отличаются. Итог: головы «отрубаются» на месте, без прыжков корпуса. Обрезка — по общему bbox всех состояний.
- **Фон-пещера.** Исходник `character-refs/фон.jfif` (1586×672, ~2.36:1) вписывается в холст «cover»-способом: масштаб по высоте, боковая обрезка (`BG_CROP_X` в скрипте) так, чтобы тёмный тоннель справа оказался за драконом, а пол-платформа — под героями. Результат `bg_cave.jpg` строго 1280×720 (`BG_SIZE` в скрипте должен совпадать с `GAME.WIDTH/HEIGHT`). Никаких эффектов поверх фона нет (прежние неоновые полосы/звёзды города убраны).
- **Размер горы золота.** Правый нижний угол кучи свисал на тёмную скалу у края платформы. Срез правой части (`MOUNT_CLIP_RIGHT`, вертикальный) пробовали и откатили — выглядело как «просто обрезанная гора». Вместо этого гора уменьшена: `MOUNT_W` 440 → 385 px на экране, якорь `DRAGON.MOUNT_X` 995 → 945 (правый край ≈ 1137, левый ≈ 752); дракон не трогали. Параметр среза остался в скрипте со значением `0.0` (`--mount-clip F`, при `0` гора целая); менять размер — `MOUNT_W` в скрипте + `DRAGON.MOUNT_X`, затем `python tools/build-sprites.py --only mountain`.
- Скрипт принимает `--only heroes lead dragon mountain bg` (плюс `--mount-clip F`) — выравнивание дракона занимает минуты, при правках фона/героев его пересобирать не нужно.
- Скрипт хранится в репозитории (отступление от прежнего «одноразовые скрипты не храним»): персонажи перегенерируются, пайплайн должен воспроизводиться.

Ключи текстур: `hero_<имя>`, `hero_<имя>_hit1..N`, `lead_cruella`, `dragon_heads0..5`, `gold_mountain`, `bg_cave`. Число поз удара задано явно полем `hits` в `config/heroRoster.json` (Скрудж — 1, Круэлла — 0, остальные — 3): `Preloader` грузит ровно их, без «пробы» несуществующих файлов (Vite dev отдаёт для отсутствующего файла `index.html` со статусом 200, и Phaser сыпал в консоль «Failed to process file»). При 404 ключа `Preloader` рисует цветной плейсхолдер.

## Раскладка сцены (`Constants.ts`)

- **Пол.** Ходибельная каменная платформа в `bg_cave.jpg` занимает y≈450–605 (1280×720); ниже ≈610 идёт кирпичная стенка платформы, а по краям — тёмные сталагмиты переднего плана. **Ноги персонажей, Круэллы и низ горы золота должны быть выше ≈605**, иначе они «сваливаются с текстуры» (это уже было: первая версия ставила ближний ряд на y=648). При смене `BG_CROP_X`/фона эти границы надо перемерить (в скрипте/по сетке поверх `bg_cave.jpg`).
- **Герои** — два шахматных ряда на полу пещеры: `HERO.SLOTS` (сейчас y=508 дальний и 578 ближний) (feet-координаты в порядке ростера слева направо). Чётные слоты — дальний ряд (выше, `scale 0.92` = перспектива), нечётные — ближний. Соседи всегда в разных рядах, поэтому широкие спрайты (Скрудж, Незнайка, Миньон ≈ 115–127 px) не налезают друг на друга; глубина = `y` ног (`setDepth`), ближний ряд рисуется поверх. Шаг по x ≈ 98 px.
- **Круэлла** — отдельно у левого края (`HERO.LEAD`), `scale 0.85`: у неё широкий шлейф (спрайт ≈ 230 px в ширину), на полном масштабе он упирался в льва.
- **Дракон и гора золота** — на правой платформе (`DRAGON.MOUNT_*`, `BODY_*`), статичны: покачивание убрано по просьбе пользователя; реакции (удар, потеря головы) трогают только tint/scale/x.
- **Текущие координаты дракона** (`DRAGON` в `Constants.ts`, холст 1280×720): гора `MOUNT_X 945 / MOUNT_BOTTOM_Y 530` (ширина 385 px), тело дракона `BODY_X 967 / BODY_BOTTOM_Y 412` (ширина 500 px, стоит на вершине кучи — при сдвиге двигать **вместе**, иначе «утонет»), точка удара `HIT_X 823 / HIT_Y 292`. Положение подбиралось по обведённой пользователем области фона (тоннель справа, основание кучи на каменной платформе).
- Рычаг для правок «слишком тесно/далеко»: `HERO.SLOTS`, `HERO.STRIKE_FRONT_X` (докуда добегает герой, см. «Удар героя»), `DRAGON.HIT_X/HIT_Y` (точка эффектов на драконе).

## Удар героя (2026-09-20)

`HeroSprite.playHit(delta)`: замах на шаг назад (`WINDUP_MS` 160) → **рывок вдоль своего ряда до подножия горы** (`RUN_MS` 280, `Quad.easeIn`, со следом-«призраками») → отдача (`RECOIL_MS` 140) → разворот (`flipX`) и возврат на слот (`RETURN_MS` 420). Раньше герой пробегал лишь 30 % пути (`min(MAX_LUNGE, 0.3·расстояния)`) и «бил сам себя»; теперь он бежит, пока **передний край спрайта** (оружие/кулак — берётся ширина текстуры выбранной позы удара) не достигнет `HERO.STRIKE_FRONT_X` = 790 (подножие кучи золота), а не центр героя.

- **Удар приходится на момент прибытия**, а не на начало события: пыль/кольцо/тряска/комикс-текст — в `onComplete` рывка; реакция дракона (`Dragon.reactToHit`), звук удара и подбадривание Круэллы — через `HERO.IMPACT_MS` (= `WINDUP_MS + RUN_MS` = 440 мс) после `MONEY_IN`. `HERO.HIT_DURATION_MS` (= сумма фаз, 1000 мс) читает `DataPollingService`, чтобы потеря голов шла после всех ударов — менять фазы, а не сумму.
- Глубина героя на время удара = глубина слота + 1 (перед соседями по ряду, но за рядом ближе к камере); после — восстанавливается вместе с `flipX`. В начале удара `killTweensOf(this)` снимает idle-наклон.
- **Отвергнутый вариант**: гнать всех в одну точку на «ближнем» ряду перед кучей (по диагонали, `y` 588, масштаб ближнего ряда). Пользователь: «герои по факту бьют кучу золота». Принят первый вариант — бег по своему ряду до подножия; ближний ряд перекрывает дальний (Миньон закрывает Льва, Незнайку и т.д. в момент удара), что «лучше, чем бить землю». Миньон стоит уже у самого подножия (передний край ≈786), поэтому почти не смещается — только сквош/отдача.

## Чёткость текста (2026-09-20)

Проблема: HUD-текст (мелкие 10–15 px Arial) выглядел размыто. Причина — вся игра рисовалась в буфер 1280×720, который браузер растягивал на экран с `image-rendering: pixelated` (это ставит `pixelArt: true`): при нецелом масштабе (1.5× на 1080p) тонкие штрихи получались неравными.

Решение (первая версия — фиксированный 2×; потом заменён выбором по устройству, см. «Производительность» ниже): **буфер 2560×1440 при логических 1280×720**. `GAME.RENDER_SCALE = 2`; `main.ts` создаёт холст `WIDTH·2 × HEIGHT·2`, а каждая сцена вызывает `fitCameraToGame(this)` (`core/Render.ts`: `setOrigin(0,0).setZoom(2).setScroll(0,0)` — зум вращается вокруг origin камеры, поэтому origin в левый верхний угол). Все координаты в коде остались логическими. Текст растеризуется с `resolution: GAME.RENDER_SCALE` (в каждом `add.text`), 2×-текстуры героев (`TEXTURE_SCALE 0.5`) попадают в пиксели буфера 1:1. `public/style.css`: `#game-container canvas { image-rendering: auto !important }` — браузер сглаживает масштабирование холста к экрану. Полноэкранные эффекты (`Fx.emitConfettiBurst/flashScreen`) считают по `GAME.WIDTH/HEIGHT`, а не по `scene.scale.*` (тот теперь возвращает размер буфера). Заодно шрифты чуть крупнее: заголовок 13, счётчик голов 16, полоса плана 18, статус/дни 12, рейтинг 13 px; панель рейтинга 184 px (сумма «1 054 000 ₽» не заезжает на код отдела); победная плашка 580 px по центру x=495 — не задевает рейтинг.

Откат: `?scale=1` в адресе страницы (или `GAME.RENDER_SCALE`/`Quality.ts`) и убрать правило в `style.css`, если нужна прежняя «пиксельная» подача. **Проверять чёткость** по `game.renderer.snapshotArea(x, y, w, h, cb)` (кроп буфера 1:1), а не по скриншоту панели превью — там холст ужат до ~0.58×.

## Производительность (2026-09-21)

**Симптом.** Раздали игру сотрудникам — на их ноутбуках (i3-6100U / i3-7020U, 2 ядра, Intel HD 520/620, 8 ГБ) после запуска браузер грузит систему на 60–100 % ЦП, видеочип 6–69 %; выставлять игру постоянно нельзя.

**Диагностика (замеры в dev-браузере, свежий пуск):**
- Сцены крошечные: `PenScene` 9 объектов, `HUDScene` 15, 19 отрисовок за кадр. Утечки нет: после 48 ударов и двух циклов «победа → сброс» счётчики объектов/твинов/таймеров возвращаются к исходным (9/15, 0 твинов), куча JS 42 МБ.
- В покое **0 активных анимаций**, но игра перерисовывалась **на каждый кадр браузера без ограничения** (`game.loop.actualFps` = 144 на моём мониторе; `fps.target: 60` — не лимит) и целиком (буфер 2560×1440 после раунда «чёткость текста» — в 4 раза больше пикселей, чем до него). То есть большая постоянная работа над неподвижной картинкой; регрессия совпадает по времени с фиксированным 2× буфером.
- На RTX 3060 стоимость кадра мизерная (замеры `EXT_disjoint_timer_query`: 0.3–0.5 мс, первые «4.6 мс» оказались артефактом состояния GPU и не воспроизвелись; от размера буфера они не зависели), поэтому **по моей машине цифры слабого ноутбука не получить** — решение опирается на структуру (что делается зря), а не на абсолютные миллисекунды. На двух из трёх скриншотов ЦП 59–100 % при видеочипе 6–25 % — узкое место может быть на стороне ЦП (в т. ч. программный WebGL), поэтому режем и пиксели, и число кадров.

**Решение.**
1. `core/Quality.ts` — профиль качества на загрузке страницы: **tier** (`low` при `hardwareConcurrency ≤ 4` или `deviceMemory ≤ 4`, иначе `high`), **масштаб буфера** = реальный размер холста на экране / 1280 в шагах по 0.25, не меньше 1, не больше 2 (1.5 для `low`), **частота в анимации** (30 для `low`, 60 для `high`), **частота в покое** (10). Для проверки на конкретной машине: `?quality=low|high`, `?scale=1.25`, `?fps=30`, `?idlefps=5`.
2. `main.ts` — холст `1280·scale × 720·scale`, `fps: { target, limit }` (лимит включает `TimeStep.stepLimitFPS`).
3. `core/PowerSaver.ts` — на лету меняет `game.loop._limitRate`: **active** (идёт конечный твин в любой сцене, либо недавно пришло `MONEY_IN` / `DRAGON_HEAD_LOST` / `DRAGON_DEFEATED` — с запасом на их `delayMs`, либо клик по холсту, либо первые 8 с после старта), **ambient** 20 к/с (идут только бесконечные «дышащие» твины — победная плашка и Круэлла держатся всю неделю), **idle** 10 к/с. Коэффициент 0.92 у лимита — чтобы на 60 Гц-мониторе кадр 16.6 мс не пропускался. `PowerSaver` ничего не делает, если `hasFpsLimit` не включён.
4. Убрано лишнее пробуждение: каждый опрос (15 с) раньше запускал пустые твины (`HUDScene.render`, `Leaderboard.update`) — теперь без изменения данных твинов и перерисовки текста нет. Покачивание персонажей — одно общее расписание (`Fx.startIdleSway`: раз в 10–16 с 2–3 случайных персонажа), а не 7 независимых таймеров (те держали игру вне режима покоя ~четверть времени).
5. Спрайты и фон получают LINEAR-фильтр (`Preloader`): при дробном масштабе NEAREST давал зубчатые края.

**Результат (замер в dev, tier `low`, реальные опросы):** в покое ~11 отрисованных кадров/с, кратковременные всплески ~28–30 к/с раз в ~12 с (покачивание), в среднем **12.5 к/с вместо 144** (и вместо 60 на типичном 60-Гц ноутбуке); удар поднимает частоту в тот же тик, через ~7 с после последней анимации возвращается в покой; каскад голов 32 к/с; победа держится на 20 к/с. Плюс буфер на слабой машине не больше 1.5× (а на HD-экране 1366×768 — 1×).

**Известные ограничения / что проверять у сотрудников.** (а) Если в их Chrome отключено аппаратное ускорение (`chrome://gpu`), WebGL идёт программно и любой кадр дорог — тогда помогает `?scale=1`. (б) Пока держится победа, экран работает на 20 к/с (пульсации) — дешевле прежнего, но не «покой». (в) Реальную нагрузку на i3 я не мерил (у меня их нет): критерий — Диспетчер задач при открытой игре в покое.

## Анимации простоя и рычание дракона (2026-09-21)

**Запрос.** Если долго нет оплат — часть персонажей может упасть или заснуть; дракон время от времени рычит и угрожающе дёргается.

**Решения (все правятся в `Constants.ts`: `IDLE`, `DRAGON.GROWL_*`).**
- **Простой считается по всей команде, а не по отделам** — чтобы упавший герой не читался как «этот отдел подводит». Источник — само событие `MONEY_IN` (любая продажа обнуляет счётчик и будит всех). Часы — **игровое время** (таймер сцены): не идёт, пока вкладка скрыта/ноутбук спит, и стартует с нуля при загрузке страницы (страница видит только продажи, пришедшие при открытой вкладке). Чтобы считать «по-настоящему» (с учётом ночи и перезагрузок), нужна отметка времени последней продажи из Apps Script (`lastSaleAt`) — не сделано, в таблице неясно, есть ли время в колонке `Date`.
- **Пороги:** через `IDLE.FIRST_MS` (1 ч) без продаж один случайный герой падает или засыпает, затем по одному за каждый `STEP_MS` (1 ч), максимум `MAX_DOWN` = 4; момент не «секунда в секунду»: каждую проверку (30 с) с шансом `DROP_CHANCE` = 0.4. Круэлла не участвует (руководитель филиала, «следит»).
- **Падение** (`HeroSprite.fallOver(dir)`): шатание → заваливание на ±90° вокруг ног (`Quad.easeIn`) → отскок; тело **приподнимается на половину своей толщины** (`y − w/2`), иначе лежащий спрайт проваливался бы под линию пола; на приземлении пыль (`emitBurst`) и глухой удар (`AudioSystem.playFall`). **Дремота** (`doze(dir)`): медленный крен ±9° и лёгкое «оседание» (scaleY 0.92). Оба состояния статичны: над героем неподвижная надпись «Zzz» и раз в 25–40 с плывёт одна «Z» (`snore()`).
- **Куда падать:** `IdleMood.freerDirection` выбирает сторону, где лежащая фигура (длина = высота спрайта) перекроет меньше всего остальных (текущий охват каждого героя, Круэлла, гора золота). Ряды тесные, поэтому лежать одновременно могут не более `MAX_LYING` = 2 — остальные дремлют стоя (иначе стопка налезающих друг на друга тел).
- **Пробуждение:** продажа → все встают по очереди с шагом `WAKE_STAGGER_MS` (`wakeUp`: возврат угла/`y`, «пружина»); герой, которому пришёл удар/празднование, встаёт мгновенно (`wakeInstant` в начале `playHit`/`playCelebrate`); победа будит всех.
- **Рычание** (`Dragon.growl`): вдох (scaleY 1.03) → дрожь `GROWL_MS`≈1.9 с (случайный джиттер x/y/угла/масштаба с затуханием, тряска камеры сцены, искры у пасти) → плавный возврат в исходную позу; звук `AudioSystem.playGrowl` — два расстроенных низких осциллятора (пила + меандр), скользящих вниз, с быстрым тремоло (27 Гц) для хрипа, через ФНЧ, который открывается и закрывается, плюс шум; тремоло стоит **до** огибающей, иначе после затухания звук продолжал бы дребезжать. Звук, как и весь остальной, выключен по умолчанию (mute). Раз в 90–180 с само по себе, чаще (40–80 с) пока команда простаивает, и через 1.3 с после каждого падения героя. Любое реальное событие (удар, потеря головы, отрастание, поражение) обрывает рычание (`cancelGrowl`) и возвращает тело в исходное положение — они трогают те же свойства.
- **Производительность.** Всё — конечные твины или статичные позы; бесконечная «дышащая» анимация держала бы слабые ноутбуки на «ambient»-частоте сутками (см. «Производительность»). При спящих героях игра остаётся в режиме покоя (~11 к/с), всплески — покачивание оставшихся, рычание, редкая «Z».
- **Показать без ожидания часа:** в адресе страницы `?idle=<минуты>` (например `?idle=1`) сжимает пороги; в dev — `__debug.mood().advance(ms)`, `.dropOne()`, `.wakeAll()`, `__debug.growl()`.

## Админка: таблица, анимации, смена PIN (2026-09-21)

**Что умеет** (вкладки `admin.html`): недельный план; **чтение** листа `Sales` (последние 50 строк, новые сверху + итоги недели и по отделам); **внесение оплаты** (отдел из ростера, сумма, дата необязательна) с подтверждением — это настоящая запись; **кнопки анимаций** (удар любого отдела с суммой, «упасть»/«заснуть» выбранному или случайному герою, «поднять всех», рычание дракона, конфетти, «все празднуют»); **смена PIN** (по текущему PIN).

**Как анимации доходят до экранов.** Админка и экраны — разные страницы, общий у них только бэкенд. Поэтому анимация — это *команда*: `POST {action:'command', type, args}` → бэкенд кладёт её в очередь (Script Properties, ключи `COMMANDS`/`COMMAND_SEQ`, последние 10, не старше 10 мин) → каждый экран получает очередь в обычном ответе публичного `GET` (поля `commands` и `serverNow`) → `DataPollingService.dispatchCommands` проигрывает каждый `id` один раз (события `ADMIN_COMMAND`, при нескольких — с шагом 0.7 с). Задержка ≈ интервал опроса (до 15 с) — отдельный частый опрос ради этого не вводился (лишняя нагрузка на Apps Script и на слабые ноутбуки). **Таблица при этом не затрагивается**: очередь — в свойствах скрипта, листы `Sales`/`Settings` команды не читают и не пишут (проверено тестом: содержимое листов до и после команд идентично).
- **Нет повторов при перезагрузке:** первый опрос после загрузки страницы — baseline (запоминается максимальный `id`), команды, выданные до открытия страницы, не воспроизводятся. Команда, которую экран увидел позже 2 минут после выдачи (был офлайн), отбрасывается; возраст считается по часам **бэкенда** (`serverNow − issuedAt`), часы компьютера не важны.
- **Чисто визуально:** `hit` идёт через обычный путь `MONEY_IN`, но с флагом `demo` (не сбрасывает счётчик простоя `IdleMood` и не будит остальных героев); `GameState` не меняется.
- **Валидация на бэкенде** (белый список): типы команд, `hero` ∈ ростер+`random`, `mode` ∈ `fall/doze/random`, сумма 0 < x ≤ 100 млн, отдел — только буквы/цифры/пробел до 20 символов (так в лист нельзя записать строку, которую таблица прочтёт как формулу: `=…`, `+…`, `@…`).

**Бэкенд (`apps-script/Code.gs`), что изменилось.** Единый роутер `doPost` по полю `action` (старый формат `{pin, plan}` без `action` понимается как `setPlan`, поэтому уже задеплоенная админка не ломается). PIN хранится как `salt$sha256` (`ADMIN_PIN_HASH`); открытый `ADMIN_PIN` продолжает работать, пока PIN не сменили из админки (тогда удаляется) — это позволяет откатить бэкенд на прежнюю версию. **Защита от подбора:** 5 неверных PIN за 10 минут → блокировка API на 10 минут (счётчик в `CacheService`; побочный эффект — злоумышленник может «держать» админку заблокированной, зато перебор невозможен). Запись в лист и очередь команд — под `LockService`; `requestId` от админки защищает от дублей при повторной отправке (кэш 10 мин).

Проверено «мутациями»: если сломать защиту от формул, блокировку или удаление старого PIN, тесты падают. `game/tools/mock-backend.mjs` отдаёт тот же `Code.gs` по HTTP (`npm run mock-backend`, PIN 1234) — на нём проверены админка и игра вместе (вход, таблица, добавление, команды до игры, отсутствие повторов, смена PIN, блокировка). **Живой бэкенд** обновляется вручную (Apps Script → Deploy → Manage deployments → New version); боевой лист `Sales` в тестах не трогался.

## Механика дракона

- `DAYS = 5` (`Constants.ts`): недельный план делится на 5 равных дневных. `GameState.headsRemaining = DAYS − floor(ratio × DAYS + 1e-9)` — единственный источник истины о числе голов (0 % → 5 голов, 20 % → 4, …, 100 % → 0). `ratio = totalThisWeek / plan`, зажат в 0..1.
- `DataPollingService.diffAndEmit` (раз в 15 с): диффит `byRop` → `MONEY_IN` на каждую положительную дельту отдела (герои бьют по очереди, `HERO.HIT_STAGGER_MS`); сравнивает `headsRemaining` с `GameState.lastHeads` → на каждую потерянную голову `DRAGON_HEAD_LOST {heads, delayMs}` (с шагом `DRAGON.HEAD_LOSS_STAGGER_MS`, если один опрос пересёк сразу несколько порогов); при `ratio ≥ 1` (и не взведён `dragonDefeated`) — `DRAGON_DEFEATED {delayMs}` после последней головы. Все задержки отсчитываются от окончания ударов этого же опроса (`settleDelayMs`), чтобы удар «читался» раньше отрубленной головы.
- **Baseline.** Первый опрос после загрузки страницы (`previous === null`) не даёт ни ударов, ни потери голов: `PenScene.onProgressChanged` ставит дракона сразу в нужное состояние. Нюанс, на котором уже обожглись: сам `create()` сцены тоже вызывает `onProgressChanged` с ещё пустым `GameState` — этот вызов не должен «съедать» baseline, поэтому флаг `hasAppliedFirstProgress` выставляется только когда `GameState.hasBaseline === true` (иначе при загрузке дракон остаётся с 5 головами, а данные говорят 4).
- **Самовосстановление.** `ratio` упал ниже порога (новая неделя/поднятый план) → `PROGRESS_CHANGED.headsRemaining` больше, чем показано → `Dragon.setHeads(n, true)` отращивает головы вспышкой, `dragonDefeated` сбрасывается, победная надпись и поза Круэллы снимаются. Отдельного отслеживания `weekStart` не нужно. Головы **уменьшаются только через `DRAGON_HEAD_LOST`** (анимированно, с задержкой); `PROGRESS_CHANGED` их только увеличивает.
- **Кто что рисует.** `PenScene` — удары героев, реакции дракона (`Dragon.reactToHit/loseHead/defeat`), Круэлла (`LeadSprite`); `HUDScene` — полоса недели с делениями «день 1…5», счётчик голов, конфетти/вспышки, победная надпись «ОТДЕЛЫ ПОБЕДИЛИ ДРАКОНА! План недели выполнен» (в левой верхней части пещеры, на пустой стене между рейтингом и драконом — по центру она закрывала самого дракона). Сцены общаются только через `EventBus`.
- **Эффекты `Dragon`**: удар — белая вспышка (`TintModes.FILL`), сквош, тряска, брызги золотых монет в сторону героя (`Fx.emitCoinBurst`); потеря головы — красная вспышка, тряска камеры, искры/кольцо/монеты, смена текстуры на пике вспышки, звук `AudioSystem.playHeadLost`; победа — серый тинт (`MULTIPLY`) + лёгкий наклон. Дракон статичен (покачивание убрано); реакции трогают только scale/tint/x — иначе твины дерутся за одно свойство.
- **Устаревшие отложенные события.** Потеря головы и победа задерживаются (удары должны «читаться» раньше), а данные за это время могут измениться — например, админ поднял план посреди каскада. Поэтому обработчики (`PenScene`, `HUDScene`) перед показом сверяются с `GameState`: потеря головы `heads` пропускается, если `heads < GameState.headsRemaining`; победа — если `!GameState.dragonDefeated`. Внутри `Dragon` число голов (`headCount`) — это **цель**: задаётся сразу при старте потери, а отложенная смена текстуры (через 140 мс) защищена счётчиком `epoch` и отменяется, если состояние успели сменить (`setHeads`/`defeat`/новая потеря). Без этого откат `ratio` в окно этих 140 мс оставлял дракона с неверным числом голов (нашли отладкой 2026-09-20).
- Каскад «5 → 0» (например, недельный план закрыт одной огромной продажей) занимает ~7 с: по 1.1 с на голову + пауза после ударов. Это сознательно — драматургия важнее скорости.

## Генерация ассетов через Fooocus (сентябрь 2026)

Fooocus (локальный SDXL-UI на Gradio, `http://127.0.0.1:7865/`) запускает пользователь сам и **вне репозитория**. Управляем им через браузер (у Gradio-API нет `api_name`, скриптовать его бессмысленно). Полный операционный справочник — скилл `~/.claude/skills/fooocus/SKILL.md` (лежит вне репо, подхватывается автоматически). Здесь — то, что важно именно для проекта:

- **Стек генерации**: чекпоинт `juggernautXL_v8Rundiffusion` + LoRA `pixel-art-xl-v1.1` (вес 1.0, offset-LoRA выключен), Performance `Speed` (30 шагов), 704×1344, Image Number 2. `Extreme Speed` (LCM) теряет «пиксельность» — не использовать.
- **Что сработало**: чистый **text2img** с промптом вида «`<персонаж и детали>, pixel art, 16-bit retro video game character sprite, full body, front-facing, symmetrical standing pose, arms visible, centered composition, plain solid white background, no background details, isolated character on white, crisp pixel outlines, limited color palette`» + негативный промпт против декоративного фона/фотореализма. Даёт узнаваемого персонажа на почти белом фоне (остаётся лёгкая серая тень под ногами — убирается при вырезании).
- **Что НЕ сработало**: img2img `Vary (Strong)` на фотореалистичных референсах (Миньон превращается в запикселенного человека), на референсах с обрезом по пояс «ног не дорисовать» (Vary привязан к структуре источника), `Inpaint or Outpaint` не принимает загрузку файла автоматикой. `Image Prompt` (IP-Adapter) даёт полный рост, но плывут пропорции. Слишком подробный текстовый промпт в img2img ломает результат — там сама картинка и есть промпт.
- **Загрузка файлов в Fooocus** возможна только через настоящий Chrome (расширение Claude in Chrome, `file_upload`); встроенная песочница-браузер файлы не грузит.
- Итоговые персонажи пользователь доработал вручную (в Photoshop, с прозрачным фоном) — в игру идут они, а не сырые выводы Fooocus.

## Надёжность и полишинг (осталось актуальным с прошлой концепции)

- **Гейтинг «громких» эффектов**: комикс-текст на ударе только при `delta >= FX.COMIC_TEXT_MIN_DELTA` — иначе экран «трещал» бы на каждой мелкой продаже.
- **Звук — сырой `AudioContext`, не `Phaser.Sound`**: нет файлов, только процедурный синтез (`systems/Audio.ts`: удар, рык при потере головы, фанфара). По умолчанию `muted=true` (офисный экран не должен шуметь без спроса), состояние в `localStorage`; `AudioContext` создаётся лениво по клику на иконку mute (user gesture).
- **Одометр** в HUD: числа анимируются tween-ом плоского числового поля на самой сцене, а не встроенной анимацией текста.
- **Живой рейтинг** (`objects/Leaderboard.ts`): строки-`Container`ы твинят `y` к новому рангу при каждом `DATA_UPDATED`; подписи — коды отделов (`RosterConfig.ropNameForSlug`), человекочитаемых имён нет и не выдумываются.
- **Idle-жизнь**: герои и Круэлла **не качаются вверх-вниз** — стоят на полу (idle-bob по `y` убран по просьбе пользователя: казалось, что они подлетают). Остался только редкий наклон раз в 20–30 с (`Fx.addIdleSway`, трогает только `angle`, пропускается, пока герой занят ударом). Твинов по `y` у героев в покое нет.
- **Ручная проверка** через `window.__debug` (только dev-сборка): `hit(heroSlug, delta)`, `setRatio(0..1)` (гонит синтетический статус через тот же diff-пайплайн, что и реальный опрос: удары, потеря голов, победа), `injectStatus(status)`, `poller.stop()` (обязательно перед ручными проверками — иначе реальный опрос через 15 с перезапишет тестовое состояние), `audio`. Проверка глазами по скриншотам ненадёжна для быстрых анимаций — состояние объектов (`texture.key`, `headCount`, `banner`) читается из `__debug.game.scene.getScene(...)`.

## Известные допущения
- **Точные колонки Google-таблицы, день начала недели** — допущения из плана, требуют сверки с реальной таблицей.

## Конвенции
- `src/game/core/` — EventBus, GameState, Constants.
- `src/game/scenes/` — Boot → Preloader → PenScene + HUDScene (параллельные).
- `src/game/objects/` — Dragon, HeroSprite, LeadSprite, Leaderboard.
- `src/game/systems/` — DataPollingService (опрос, диффинг по РОПам, потеря голов), RosterConfig, Audio, Fx (переиспользуемые VFX без ассетов).
- `src/game/config/` — `heroRoster.json` (ростер: slug/sprite/color/lead), `ropMapping.json` (код отдела → slug героя), правятся отдельно от кода.
- Все «магические числа» — в `Constants.ts` (раскладка, тайминги, `DAYS`).
